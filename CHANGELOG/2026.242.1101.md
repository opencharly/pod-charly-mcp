# 2026.242.1101 — fix: seed a placeholder project into /workspace

## Summary

Fixes opencharly/charly#480.

The candy creates `/workspace` world-writable and points `CHARLY_PROJECT_DIR` at it, but never puts a project there. So `charly mcp serve` starts with no project, the plugin's project prefix resolves to `--repo default`, and — because that prefix is computed **once at server startup** and closed over by every tool handler — every project tool then runs

```
git ls-remote --symref https://github.com/opencharly/charly.git HEAD
```

from **inside the venue**, for the lifetime of the process. In a pod without egress DNS that is a hard failure of `version`, `box.list.boxes` and `charly status --json`, and it does not recover when a project appears later.

A bind-mount over `/workspace` shadows the seeded file, so an operator mounting a real checkout is unaffected. This only decides what happens when nothing is mounted.

## How tested

**A/B in the failing venue** — the `check-debian-coder-pod` pod, which has no DNS (`getent hosts github.com` fails). Same supervised service, same env, same cwd, **stock plugin both times**; the only variable is `/workspace`:

```
### STOCK plugin + EMPTY /workspace
… cannot resolve --repo "default": resolving default branch for github.com/opencharly/charly:
  git ls-remote --symref … HEAD: exit status 128 …  "isError":true

### STOCK plugin + seeded /workspace
{"jsonrpc":"2.0","id":2,"result":{"content":[{"type":"text","text":"2026.229.1921\n"}]}}
```

Both previously-failing tools recover with the seeded project in place:

```
### version
{"result":{"content":[{"type":"text","text":"2026.229.1921\n"}]}}
### box.list.boxes
{"result":{"content":[{"type":"text","text":""}]}}
```

(`box.list.boxes` is empty because the placeholder declares no boxes — a successful empty result, not an error.)

**Why the stamp is the migrate floor and not a CalVer.** The correct stamp is a property of the charly baked into *this* image and cannot be known when authoring the candy. Both directions are rejected:

```
# stamp NEWER than the image's charly
config schema 2026.232.0520 is newer than this charly supports (max 2026.225.1508)

# stamp OLDER — box validate refuses it too
schema 2026.225.1508 is required (found "2026.100.0000")

# and migrate will not lift an arbitrarily old one
schema "2026.100.0000" predates the supported floor 2026.174.1100
```

Seeding at the floor and letting the image's own charly restamp is the only image-independent option, and it works:

```
$ head -1 /workspace/charly.yml          ->  version: 2026.174.1100
$ charly migrate -C /workspace           ->  migrated to schema 2026.225.1508
$ head -1 /workspace/charly.yml          ->  version: 2026.225.1508
$ charly box validate                    ->  rc=0
```

on an image whose `charly version` reports `2026.229.1921`.

The placeholder is deliberately **distro-agnostic** — a `mkdir` run step plus a check, no `distro:` package — because a `debian:` package list would be wrong on the arch- and fedora-based images that also compose this candy. An earlier shape with only a check step failed validation (`must have at least one install file`); the marker directory satisfies it without pinning a distro.

Candy gate on the committed tree:

```
$ charly box validate
validate exit=0
```

## The seeding step executing at image build (fresh rebuild)

The first revision of this body proved the seeded *end state* fixes the tools but not that the seeding *mechanism* runs at build — a fair block. Here it is, from a fresh build of a minimal probe box composing this candy (`base: debian`, local candy shadowing the remote pin, built on a separate `CONTAINERS_STORAGE_CONF` graphroot):

```
$ charly box validate
Note: local candy "charly-mcp" shadows remote candy "github.com/opencharly/pod-charly-mcp"
validate exit=0

$ charly box build mcp-probe
[22/22] STEP 35/63: RUN mkdir -p /workspace && chmod 0777 /workspace
[22/22] STEP 36/63: COPY --chmod=0666 .build/mcp-probe/_inline/charly-mcp/07576e8f8fcc… /workspace/
[22/22] STEP 37/63: RUN --mount=type=bind,from=charly-mcp,… charly migrate -C /workspace
migrated to schema 2026.225.1508
…
Successfully tagged ghcr.io/opencharly/mcp-probe:2026.242.1059
build exit=0
```

STEP 36 is the `write:` step placing the placeholder; STEP 37 is the migrate step restamping it to the image's own schema. And the artefact is in the resulting image:

```
$ podman run --rm ghcr.io/opencharly/mcp-probe:2026.242.1059 sh -c 'head -3 /workspace/charly.yml; ls -la /workspace/charly.yml'
version: 2026.225.1508
workspace:
    candy:
-rw-rw-rw- 1 root root 722 Aug 30 11:00 /workspace/charly.yml
```

Seeded at the migrate floor, restamped to `2026.225.1508` by the image's own charly, world-writable so a later bind-mount or edit is unobstructed. Together with the A/B above — which shows that exact end state fixing both failing tools in the DNS-less venue — the chain is complete: the step runs at build, and what it produces is what makes the tools work.

## A wrong fix I published first, and withdrew

I originally attributed this to `plugin-mcp`'s `computeProjectPrefix` statting `charly.yml` in the process CWD while the venue points at `CHARLY_PROJECT_DIR`, and opened opencharly/plugin-mcp#4. A reviewer blocked it for having no live run of the changed branch. Doing that run falsified it: the supervised service's cwd already **is** `/workspace`, so the existing cwd stat covers it and my branch never changed the outcome — the A/B above reproduces and fixes the failure with the **stock** plugin.

What misled me was testing against the long-running supervised server: it had computed `--repo default` at pod boot when `/workspace` was empty, and kept it, so seeding a project appeared not to help. It helps on restart. That PR is closed with this explanation rather than landed as speculative hardening.
