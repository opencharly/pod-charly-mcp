# 2026.270.0621 — fix(layer-charly): pin the deterministic charly version (v2026.269.2324)

## Summary

Bump the `charly-mcp` candy's `layer-charly` pin from `v2026.243.0408` to
`v2026.269.2324` — the `layer-charly#10` tag that makes the baked charly version
**deterministic** (the old tag installed a floating charly).

This is the **producer leg** of the cross-repo chain required to bring the
self-hosted GitHub runner image onto the deterministic charly:

```
opencharly/layer-charly#10 (merged, tag v2026.269.2324)
  -> this PR (pod-charly-mcp pins the new tag)
  -> opencharly/distro-cachyos (bump its pod-charly-mcp pin + its direct layer-charly pins)
  -> rebuild + redeploy charly-githubrunner-no-{1..4}
```

Why it is needed: `distro-cachyos`'s shared `charly-marketplace` closure pulls
in this candy, so as long as pod-charly-mcp still pins `layer-charly:v2026.243.0408`,
bumping `distro-cachyos`'s own `layer-charly` pins makes the resolver emit a
`resolved to multiple versions` warning — and a change that introduces a version
mismatch is not landable under the zero-warnings rule. Bumping the producer is
the root fix (no workaround).

## How tested

**Two-sided proof at the repo's OWN pinned charly** — the exact tag
`.github/workflows/deploy.yml` clones (`v2026.241.1121`), built from source the
same way CI does (`cd charly && go build -buildvcs=false ...`):

```
$ git clone --depth 1 --branch v2026.241.1121 https://github.com/opencharly/charly.git /tmp/charly-old
$ (cd /tmp/charly-old/charly && go build -buildvcs=false -ldflags "-X main.BuildCalVer=2026.241.1121" -o /tmp/charly-old/bin/charly .)
$ /tmp/charly-old/bin/charly version | tail -1
2026.241.1121
```

**CONTROL — a bogus pin proves the ref IS resolved by the gate (not vacuous):**

```
$ sed 's|layer-charly:v2026.269.2324|layer-charly:v9999.999.9999|' charly.yml > /tmp/ctrl/charly.yml
$ (cd /tmp/ctrl && /tmp/charly-old/bin/charly box validate); echo "exit=$?"
charly: error: command "validate": validation error: downloading github.com/opencharly/layer-charly:v9999.999.9999: InvokeProvider refs:refs op=resolve: resolving ...: could not resolve ref "v9999.999.9999" in https://github.com/opencharly/layer-charly.git
exit=1
```

**WITHOUT the change (`origin/main` manifest) → exit 0:**

```
$ (cd /tmp/pcm-main && /tmp/charly-old/bin/charly box validate); echo "exit=$?"
exit=0
```

**WITH the change (bumped manifest) → exit 0:**

```
$ (cd /tmp/pcm-bump && /tmp/charly-old/bin/charly box validate); echo "exit=$?"
exit=0
```

So the local composition, the consumer `distro-cachyos` PR, and this repo's real
CI `candy` job (which builds the same pinned charly and runs the same command)
all agree: the bump resolves `layer-charly@v2026.269.2324` cleanly (the control
fails, the bumped tree passes).
