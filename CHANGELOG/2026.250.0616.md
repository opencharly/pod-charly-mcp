# 2026.250.0616 — charly-mcp: carry the project location via service working_directory, not CHARLY_PROJECT_DIR

## Summary

The charly-mcp candy set `CHARLY_PROJECT_DIR=/workspace` unconditionally in its `env:` block and ran `charly mcp serve --listen :18765` as a supervisord service. Under the no-env-stripping principle (P2 — children inherit the full environment), an unconditional `CHARLY_PROJECT_DIR=/workspace` pointing at an EMPTY /workspace (no bind mount) would make the MCP server's child commands resolve /workspace and fail with no project — breaking the auto-fallback to the default repo.

The fix carries the project location via the service's `working_directory` instead of an env var:

- **Service entry:** added `working_directory: /workspace` (the service schema supports it; supervisord renders it as `directory=`). The server's cwd is now /workspace, `computeProjectPrefix` checks cwd for charly.yml, and the child inherits cwd.
- **env block:** removed `CHARLY_PROJECT_DIR: "/workspace"` entirely (a comment-only `env:` block is schema-invalid — YAML parses it as null against the map type — so the explanation moved to the service entry).
- **Skill content:** updated the same-file `charly-mcp-skill` node's references to the old env-var mechanism (description, Candy Properties table, "How the fallback fires") so the shipped documentation matches the new working-directory mechanism.
