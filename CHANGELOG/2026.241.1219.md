# 2026.241.1219 — feat: extract the charly-mcp candy into its own repo

## Summary of changes

Phase D of the approved cutover, the last of the 13 D.1 candies: extract `charly-mcp` out of
`charly/candy/` into its own kind-prefixed repo. **`pod-`** rather than `layer-` because the candy
declares a `service:` and `port: 18765` (`plan/candy_to_repo.md`'s naming rule, enforced by
`refs_sweep_test.go:42`).

`charly/candy/` is the marketplace corpus's second input path — it reaches the corpus only because
CI clones charly at a hand-written tag, which is how a stale pin can freeze skill content while
every gate stays green. This candy owns **1 `skill:` entity**.

### One line differs from the charly source, and it is load-bearing

The candy's closure named the `charly` meta-candy by **bare word**:

```yaml
candy:
    - charly
```

A bare word resolves only inside charly's own project closure. Extracted verbatim the candy does
**not** validate:

```
charly: error: command "validate": validation error: candy "charly-mcp" candy: unknown candy "charly"
```

That meta-candy is now its own repo (`opencharly/layer-charly`, merged earlier in this phase), so
the reference becomes an explicit pin:

```diff
         candy:
-            - charly
+            # the charly meta-candy, now its own repo (candy de-submodule cutover)
+            - '@github.com/opencharly/layer-charly:v2026.241.1216'
```

This is the same dependency, stated where it is used instead of inherited from an ambient closure.
Nothing else in the manifest changes — the `skill:` entity is untouched, so the generated corpus is
unaffected.

**Ordering note:** this candy could not be extracted before `layer-charly` existed and was tagged.
That dependency was not in the plan's D.1 table; it surfaced from the standalone-validate gate,
which is why that gate runs before `gh repo create`.
